01 · Ownership model

The packaging leaf owns it. The library never does.

Three candidates were on the table. Only one of them can answer the question the charge exists to answer — what caused this money?
Packaging leaf
recommended
The component attachment on this quote — 10064-GNX-Box under FIX-ASY-B. Print plates exist because that carton has artwork. Dies exist because that carton has geometry. Attribution is causal, not organizational.
Item group
too coarse
Works only while a group holds one carton. The moment FIX-ASY-B holds two, the group cannot say which one caused the plate — and swapping a component silently reassigns the charge to a cause that never existed.
Library definition
wrong layer
The library is a catalogue of what exists. A charge is a record of what a project incurred. The library may remember that this carton class usually causes plates; it may never hold the dollar that a quote agreed to.
Ownership is polymorphic, and quote-level ownership does not go away
Project setup, container freight and duty are caused by the project, not by a component. If component ownership becomes the only owner type, operators will hang freight off an arbitrary carton to make the form accept it — and the attribution becomes a lie that survives to NetSuite. So the field is an owner reference with two v1 types:
owner.type = quote
owner.type = component_attachment  ← new
owner.type = item_group  · deferred
Never nullable. An unowned charge is the state the current model already suffers from, and it is what makes freight/duty attribution guesswork today.
Amendment required · costs-page-layout §1 and §9
That document's load-bearing claim is “per-unit costs have a SKU dimension; one-time costs don't — that is why the one-time section appears once at the foot.” Half of it stops being true: an owned charge has an owner dimension. The economy survives, because the section's rows were always lines rather than SKUs and it already carries the tier grid. The correction is narrow: rows group under their owner; the section still appears once; tier column positions are unchanged. Quote-owned charges group under a Project heading, which is the honest name for what that section has always held.
02 · V1 charge vocabulary

Five governed types, and Other as the instrument that grows the list

A governed type earns its place by having a distinct cause, a distinct NetSuite destination, and a distinct recovery policy. Two of the proposed eight fail that test, one is a component rather than a charge, and two collide with each other.

Other requires an operator label and is the measuring instrument, not the escape hatch. Label frequency gets reviewed quarterly; a label that clears a threshold graduates into a governed type with a real destination and policy. That is how the vocabulary earns growth instead of being guessed at now.
Cartons
not a charge
A carton is a component with a per-unit cost. Put it in the one-time list and it gets counted twice — once on the packaging line, once as a charge — and the second copy is invisible in the cost stack. If the real gap is “master carton isn't modelled as a component,” fix it in components.
Processing fee
defer to Other
A type that means anything absorbs everything. Ship it and within a quarter it outnumbers the five real types, with no destination mapping worth having. Let it arrive through Other; if it earns the volume, it graduates with a definition someone had to write.
Print plates ∥ Artwork / plates
collision
Two types containing the word “plates” is a coin flip at entry and unreconcilable in reporting. Split by what is bought: Print plates is plate and cylinder making; Artwork & prepress is design and adaptation labour. Distinct causes, distinct destinations.
02a · resolved · raised by CA
Artwork & prepress is one-time. The per-SKU basis was a symptom of having no owner.
You are right that it reads inconsistently, and the inconsistency is inherited rather than proposed. Today's fixture carries Artwork & plate · per SKU · 3 SKUs because the charge had nowhere to live: adaptation labour is genuinely bought once per component, so with no component to own it, the only way to express “three cartons' worth” was a per-SKU multiplier on a single quote-level row.

Three rows, three causes, independently priceable and independently recoverable. The multiplier disappears because the thing it was standing in for now exists.
Rule: every component-owned charge has basis one_time. No exceptions, and the sheet never asks — the screen is called Add one-time charges and it means it. per_sku survives only on quote-owned charges, as a legacy basis, and it should be treated as deprecated: every case it currently expresses is a component-owned charge that had no owner. If a genuinely recurring per-SKU artwork cost exists, it is a per-unit cost belonging in the packaging cost stack, not a charge — and that is a separate finding, not this screen's problem.
The picker's basis column is now fixed text rather than a per-type value, which also removes an entry-time decision the operator was never qualified to make.

06 · Required data model

A target shape to reconcile against, not a subsystem to build

Reframed · raised by CA
Taken as written, the table below is a parallel charge subsystem, and that is the wrong reading of it. Nexus already carries governed recovery, approval voiding, freeze and NetSuite mapping against the existing (quote, charge_key) grain — infrastructure that took rounds to get right and that nothing here disputes. Read this as the shape the existing model needs to reach, and let engineering choose the route. The design's actual requirements are three, and all three are additive:
01
An owner reference on the charge — the one genuinely new field. Existing rows migrate to owner = quote, which is what they already mean.
02
Instance grain instead of key grain — charge_key becomes a type reference and stops being the identity. This is the one change with real reach, because recovery, freeze and the send checklist all address charges by key today.
03
A charge-type registry with a template map — the only wholly new table, and it holds no economics, so it carries no migration risk.
Everything else below already exists in some form. If engineering finds that instance grain is reachable by widening the existing key rather than replacing it, that is a better answer than this table and the design does not care which is chosen.
