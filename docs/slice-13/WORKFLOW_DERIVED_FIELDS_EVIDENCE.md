# Workflow-Derived Fields Ownership Evidence

## Executive conclusion

Nexus is not authorized to write any additional workflow-derived, sourced, or
generated Sales Order field identified in this packet.

Repository evidence proves that Nexus creates a Sales Order with a bounded
header and flat-line payload, receives the generated internal ID from the
`Location` header, and performs one narrow readback for the generated
`tranId`. The current payload deliberately omits historical, opportunity,
SuiteTax, third-party bundle, job, and origin-linkage fields. Release-blocking
tests protect those omissions.

The repository also contains a historical parity probe that enumerates fields
returned by NetSuite but not sent by Nexus. It characterizes many as generated,
sourced, workflow-populated, or SuiteTax-derived. Those characterizations are
useful discovery evidence, but the repository contains no active NetSuite
workflow, SuiteScript, transaction-form, SuiteTax, or third-party bundle
export. Except for native record identities and arithmetic or lifecycle
results whose NetSuite ownership is intrinsic to their observed role, the
exact automation owner remains unproven.

This report therefore:

- recommends `NETSUITE_DERIVED` for native identity, date, financial, sourced
  line, address, and lifecycle result fields;
- retains `UNKNOWN` for custom workflow, Opportunity/Job propagation, report
  timestamp, and third-party bundle fields until administrator and sandbox
  evidence identify the writer;
- preserves `HISTORICAL_INACTIVE` for the retired project-generation trigger
  in the current Nexus contract; and
- authorizes no new Nexus write.

No permanent parity-matrix value or existing evidence conclusion is changed by
this packet.

## Scope and evidence boundary

This packet follows
[Data Traceability and Field Governance](../architecture/DATA_TRACEABILITY_AND_FIELD_GOVERNANCE.md)
and covers Sales Order fields that repository evidence suggests are populated,
sourced, calculated, mutated, or generated by:

- NetSuite native record behavior;
- server-side sourcing;
- NetSuite Workflow;
- SuiteScript or third-party bundle automation;
- SuiteTax; or
- downstream transaction lifecycle activity.

The [Project Manager evidence](PROJECT_MANAGER_PROPAGATION_EVIDENCE.md) and
[Standard Terms evidence](STANDARD_TERMS_OWNERSHIP_EVIDENCE.md) remain
independent and unchanged. Item Group construction is not investigated here.
Fields Nexus actively and unconditionally writes are not reclassified merely
because NetSuite returns them. The conditional `taxCode` omission path is
included because NetSuite derives that value when no approved Nexus override
is configured.

This is repository-first evidence only. No production write, sandbox write,
metadata query, workflow execution, or parity-matrix update was performed.

## Evidence terminology

- **Confirmed repository evidence**: executable code, schema, tests, fixtures,
  version history, or committed documentation establishes the statement.
- **Inference**: a historical probe label or known field role supports a
  probable mechanism, but active configuration is absent.
- **Administrator evidence required**: metadata or active NetSuite
  configuration must identify the field, writer, trigger, order, and owner.
- **Sandbox evidence required**: an owned transaction must establish immediate
  and post-automation values.

The evidence levels used in the inventory are:

- **R1 — executable**: active builder, completion code, or regression test;
- **R2 — repository observation**: a committed parity probe or recorded
  structured observation;
- **R3 — historical narrative**: a committed comment or planning record;
- **A — administrator required**; and
- **S — controlled sandbox observation required**.

R2 and R3 evidence identify candidates; they do not authorize ownership.

## Confirmed current Nexus boundary

The active path is:

1. `src/lib/netsuite/mark-complete.ts` builds the accepted quote's Sales Order
   input.
2. `src/lib/netsuite/sales-orders.ts` centralizes the outbound body.
3. `createSalesOrder` posts that body to the NetSuite `salesOrder` record
   endpoint with a deterministic idempotency key.
4. NetSuite returns the internal record ID in the response `Location` header.
5. Nexus reads back only `tranId`; failure to read it is non-blocking and is
   retried during completion convergence.
6. Nexus does not read back or reconcile any other candidate field in this
   packet.

`tests/unit/sales-order-accounting-contract.test.ts` proves that the builder
omits `custbody_dps_auto_generate_project`, `custbody_report_timestamp`,
`custbody_dps_related_opportunity`, all three SuiteTax after-discount fields,
all three third-party bundle line fields, `opportunity`,
`previousOpportunity`, `job`, and `createdFrom`.

The historical `scripts/parity/so-field-parity.ts` fetched a newly created
Sales Order and a workflow-created reference Sales Order with expanded
subresources, then enumerated response differences. Its
`INTENTIONAL_DIFF_REASONS` labels are the source of most candidates below.
The script does not persist a structured result, capture before/after
automation states, or prove active production and sandbox configuration.

## Confirmed repository evidence

- The active Nexus builder does not write the candidate custom workflow,
  SuiteTax, bundle, Job, Opportunity, origin, generated, or rollup fields
  listed above.
- The builder sends explicit line quantity and rate but omits line `amount`.
- The builder omits line `taxCode` when no firm-level override is configured
  and documents NetSuite tax derivation as the intended default path.
- Sales Order creation returns an internal ID; Nexus separately reads only the
  generated `tranId`.
- The accounting-contract test makes key historical, custom automation,
  SuiteTax, bundle, Opportunity, Job, and origin omissions release-blocking.
- No active NetSuite Workflow, SuiteScript, transaction-form, SuiteTax, or
  third-party bundle definition is versioned in this repository.
- The committed accounting universe requires production and sandbox evidence
  before classifying returned fields.

## Inferences

- Native identifiers, timestamps, totals, line identities, item metadata, and
  lifecycle quantities are probably owned by NetSuite because the historical
  probe observes them only in returned records and describes their record or
  transaction context.
- `custbody_report_timestamp` is probably written by a workflow, SuiteScript,
  or reporting bundle because it is a custom field described as a processing
  timestamp; its exact writer is unknown.
- Opportunity and Job linkage probably differs between converted legacy
  transactions and Nexus direct creation. The repository does not prove which
  active workflow, script, or sourcing rule owns those fields.
- The three `custbody_stc_*` values are probably SuiteTax or tax-bundle
  outputs, but the acronym and historical comment do not identify the active
  deployment.
- The three unrecognized custom line fields are probably bundle-owned, but
  their names alone do not establish purpose or ownership.

No inference in this section authorizes a write or a parity classification.

## Administrator evidence required

The NetSuite administrator must provide:

1. Sales Order body and line field metadata, including display label, type,
   source, default, store-value behavior, and scriptability.
2. Active transaction forms and their sourcing/default configuration.
3. Active Workflows with trigger events, conditions, field actions, execution
   order, release status, and production/sandbox deployment.
4. Active User Event, Client, Scheduled, Map/Reduce, and other SuiteScript
   deployments that read or write candidate fields.
5. SuiteTax and related bundle configuration for calculated header and line
   results.
6. Installed-bundle ownership and documentation for the three unrecognized
   custom line fields.
7. Sales Order numbering, date, inventory commitment, costing, pricing,
   shipping-address, and project-generation preferences.
8. The current business and technical owner for every custom automation.
9. A production/sandbox comparison for all relevant forms, preferences,
   workflows, scripts, bundles, and fields.

Accounting and Operations must identify which candidate fields affect
invoicing, fulfillment, purchasing, tax, revenue, reporting, project
operations, or customer documents. A returned field that has no business
consumer may remain observational rather than becoming a Nexus dependency.

## Sandbox evidence required

After metadata and ownership are known, use owned sandbox transactions to
capture:

1. the exact outbound Nexus payload;
2. the immediate create response and immediate expanded Sales Order;
3. observable workflow/script completion rather than an arbitrary wait;
4. the post-automation expanded Sales Order;
5. system notes, workflow history, and script execution evidence;
6. downstream changes after partial fulfillment, billing, close/reopen, and
   other relevant lifecycle events;
7. line arithmetic, totals, tax, costing, inventory, address, and reference
   reconciliation; and
8. cleanup of only records proven to belong to the probe.

At least two representative source records are required where Customer, item,
tax, location, project, or transaction-form defaults can change the outcome.
Sandbox observations must be compared with read-only production observations
and configuration before claiming parity.

## Ownership decision

The recommended classifications in this packet are provisional governance
outcomes:

- Native record identities, arithmetic rollups, sourced item facts, and
  lifecycle state should be owned as `NETSUITE_DERIVED`.
- Custom fields whose writer is not versioned remain `UNKNOWN`, even when a
  historical comment calls them generated or workflow-populated.
- Fields proven to be written by an active workflow, SuiteScript, or bundle
  should move to `NETSUITE_WORKFLOW_OR_SCRIPT_OWNED`.
- `custbody_dps_auto_generate_project` remains `HISTORICAL_INACTIVE` for the
  current Nexus contract.
- Nexus may read a confirmed result as a
  `SHARED_READ_ONLY_DEPENDENCY` only when a business workflow requires it and
  missing/stale behavior is defined.

These classifications must not be copied into the permanent parity matrix
until the field-specific evidence gate is satisfied and approved.

## Decision gate

No candidate field may be added to the Nexus payload until:

- its exact metadata and display name are known;
- its current writer, trigger, timing, and operating owner are evidenced;
- immediate and post-automation values are captured;
- null, omission, invalid, stale, and changed-source behavior is known;
- production and sandbox configuration differences are traced;
- Accounting or Operations identifies the business consequence;
- exactly one ownership classification is approved;
- duplicate-write and overwrite risks are resolved; and
- reviewers can answer:
  1. Who owns this field?
  2. Why should Nexus write it instead of relying on the owning system?

If an existing NetSuite mechanism owns the field, the Nexus checkpoint should
provide validation, reconciliation, or safe missing-dependency handling—not a
second writer.

## Recommendation

**Nexus should not write any newly inventoried workflow-derived, sourced, or
generated field.** Preserve current omissions. Collect administrator exports
first, then run controlled before/after sandbox probes only for fields that
Accounting or Operations confirms are material. Promote a field from
`UNKNOWN` only through the documented governance gate, and implement a Nexus
write only if ownership is explicitly transferred to Nexus.
